## 三、遇到的坑与解决

真实项目里 debug 花的时间往往比设计还多，记录下来以后遇到能快速定位。

### 坑 1 · npm workspace 语法不识别
`workspace:*` 是 pnpm/yarn 语法，npm 不认。改成 `"*"` 让 npm workspaces 自动软链。

### 坑 2 · Prisma migrate 显示"data loss"被取消
删除列（recommendCount、deepReadRatio）+ 加唯一索引会触发破坏性变更提示。解决：`npx prisma migrate reset --force` + 手动跑 `prisma migrate dev --name xxx` 生成新迁移文件。

### 坑 3 · tsx + Playwright 的 `__name is not defined`
tsx（esbuild）编译 TS 时会给函数加 `__name(fn, name)` 包装。这个函数在 Playwright 的 `page.evaluate` 里跑就爆了（浏览器上下文没定义）。解决：`page.addInitScript({ content: 'globalThis.__name = (fn) => fn' })`，字符串形式注入避免被 esbuild 二次处理。

### 坑 4 · XHS 反爬识别 Playwright 的 CDP navigate
`page.goto()` 走 CDP `Page.navigate` 命令，XHS 会针对这个信号丢流量。**手动地址栏输入却没事**。解决：改用 `page.evaluate(() => window.location.href = url)` 模拟用户手动导航。

### 坑 5 · Playwright 自带 Chromium 被 XHS 深度检测
即使 Stealth 补丁全套上，Chromium 二进制指纹还是与真实 Chrome 有差别。解决：`channel: 'chrome'` 让 Playwright 用系统安装的真实 Chrome。

### 坑 6 · Chrome profile 被锁 → context 已关闭错误
Playwright 用 `launchPersistentContext` 时，如果同一 profile 目录被其他 Chrome 进程占用，会失败或半途崩溃。解决：
- 在 `getContext()` 加 context 存活检测
- context.on('close') 事件重置 promise 让下次自动重启
- 提示用户 Cmd+Q 彻底退出 Chrome

### 坑 7 · Chrome 窗口的小圆点
macOS Dock 上 Chrome 图标下的小圆点=Chrome 进程还在跑。窗口关掉不等于退出。得 Cmd+Q。

### 坑 8 · 标题抽取召回率低
初版只匹配括号里的英文，博主不带括号写标题就漏。改进：加"纯英文长短语"识别（按中文标点切段，每段找连续英文短语）。召回率从 2/20 提升到 19/20。

### 坑 9 · Prisma 事务超时
在长事务里做 20+ upsert + 长时间的 arXiv API 反查 → 超过 5 秒默认超时。解决：
- 事务外做 arXiv 反查
- 事务超时改 30s、maxWait 10s
- BloggerPost upsert 移出事务（不需要与 paper 原子）

### 坑 10 · Body cannot be empty
Fastify 严格：Content-Type: application/json + 空 body 会报错。前端 client 改为：`hasBody ? Content-Type: application/json : 不设`。

### 坑 11 · Zod `.optional()` 不接受 null
Prisma 空字段返回 null，Zod `.optional()` 只允许 undefined，导致校验失败。全改成 `.nullish()`（接受 null 和 undefined）。

### 坑 12 · buildUrl 绝对 URL 变相对
前端 `buildUrl` 用 `new URL(...).pathname` 返回，如果 BASE_URL 是绝对 URL 会丢 host。加分支：绝对 URL 返回 `url.toString()`，相对返回 pathname+search。

### 坑 13 · SSE 绕过了 CORS 头
Fastify `reply.raw.writeHead` 会绕开 `@fastify/cors` 插件。手动在 SSE 头里加 `Access-Control-Allow-Origin` + `Access-Control-Allow-Credentials`。

## 五、部署到生产的演进路线

**核心问题**：登录态 cookie 现在靠开发者手动跑 `xhs:login`，真实用户不可能这么用。

### 阶段 1（当前）· 本地单用户
- 终端跑 `xhs:login`，cookie 保存到 `.crawler-profile/`
- **适用**：开发调试

### 阶段 2 · 单用户云端部署
- 云服务器（Fly.io / Railway）跑后端
- SSH 进服务器跑登录脚本 · 或做受保护的 admin API 触发登录流程
- **适用**：你自己用的云版本

### 阶段 3 · 小规模多用户
每个用户提供自己的 XHS 登录态。三种方案：

**方案 A · 用户粘贴 Cookie**
- 应用里加"XHS 账号设置"页
- 用户按引导从 Chrome DevTools 复制 cookie
- 后端加密存储，抓取时用该用户的 cookie
- **优点**：无需托管浏览器，成本极低
- **缺点**：技术门槛高、UX 差、cookie 过期需要重复操作

**方案 B · 应用内 WebView 登录**
- 内嵌 iframe/popup 加载 xhs 登录页
- postMessage 或 CDP 传回 cookie
- **注意**：XHS 大概率禁止 iframe 嵌套（X-Frame-Options）
- **需要**：独立 popup 窗口 + 后端配合

**方案 C · 浏览器扩展**
- 提供 Chrome 扩展，用户装完一键上报当前 cookie
- **优点**：UX 最好
- **缺点**：需开发扩展 + Web Store 审核

### 阶段 4 · 规模化
用户到几百上千级：
- **托管浏览器服务**：Browserless、Bright Data、ScrapingBee 等
- 后端调用他们的 API 做爬取，反爬 + IP 池 + 登录态都是他们负责
- **成本**：$50-500/月，每次抓取几美分

### 我推荐的选择

**如果给你自己 + 几个同事用**（≤10 人）：走**阶段 3 方案 A**（粘贴 cookie），大约 1-2 天工作量。

**如果做面向公众 SaaS**（≥100 人）：走**阶段 3 方案 C + 阶段 4**（扩展 + 托管服务）。

**根本方案**：降低对 XHS 的依赖，多元化数据源（arXiv、Twitter API、RSS、微信公众号 rsshub 等）。XHS 是敌对反爬关系，任何绕过方案都是持续维护成本。

## 六、当前使用手册（本地开发）

### 常规使用
```bash
# 起数据库（Supabase 已经在跑，跳过）
# 起后端
npm run api:dev

# 起前端
npm run dev
```

前端 http://localhost:5173 用 `demo@inspire.local` / `demo1234` 登录。

### 首次或 cookie 过期时登录
```bash
cd apps/api
npm run xhs:login
```

弹出 Chrome 窗口 → 手动扫码登录 → 关闭窗口 → 登录态保存到 `apps/api/.crawler-profile/`。

### 添加博主
在博主管理弹窗里选平台"小红书"，粘贴博主主页链接或用户编码（20-32 位十六进制字符串），点添加。爬虫后台跑，进度可看。

### Cookie 过期检测
如果爬取失败且博主管理弹窗顶部出现琥珀色横幅"小红书登录态已失效"，按横幅提示重跑登录脚本即可。
